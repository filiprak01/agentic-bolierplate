Od czystego komputera do działających agentów

Kompletna lokalna konfiguracja operatora, PO Inbox, workerów Docker oraz wykonania Codex przez subskrypcję ChatGPT na hoście.

Docker Compose Operator UI + API Wiele ról Jira + GitHub Codex subscription Durable resume

Najpierw: uczciwa granica 1.2.0

Co działa Kontenery uruchamiają UI, API, trwałe usługi i pętle wszystkich ról. Workery rejestrują się, odpytują przydziały, sprawdzają blokady i zapisują stan. Hostowy supervisor wykonuje zadania Codex z użyciem zalogowanej subskrypcji ChatGPT.
Czego 1.2.0 nie udaje Poświadczenia ChatGPT nie są kopiowane do kontenerów. Codex nie działa autonomicznie wewnątrz zwykłego obrazu workera. Wykonanie przechodzi przez codex app-server i supervisor uruchomiony na hoście.
Jira / PO Inbox→Scheduler + role worker→Durable Codex job→Host supervisor→Codex subscription

1. Ustal katalogi

Nie mieszaj platformy, projektu docelowego i roboczych checkoutów agentów. Dla pierwszego projektu użyj takiego układu:

WSL · rekomendowany układ
/home/user/business/
├── agentic-bolierplate/          # platforma 1.2.0
├── projects/
│   └── my-project/               # właściwe repo projektu
└── agent-workspaces/             # izolowane checkouty agentów
  • TARGET_PROJECT_PATH wskazuje właściwe repo projektu.
  • data/ platformy przechowuje inbox, limity, joby, wyniki i logi; nie usuwaj go przy zwykłym restarcie.
  • Każdy agent dostaje osobny workspace i branch feature/<JIRA-KEY>-<slug>.
  • Nie pracuj bezpośrednio na main.

2. Pobierz stabilny release

Dla środowiska operacyjnego używaj gałęzi release. Tag służy do niezmiennej inspekcji i odtworzenia dokładnego snapshotu.

Nowa instalacja
cd /home/user/business
git clone --branch release/1.2.0 \
  git@github.com:example-org/agentic-boilerplate.git
cd agentic-bolierplate
git fetch --all --tags
git status --short --branch
Istniejący checkout
git fetch --all --tags
git switch release/1.2.0
git pull --ff-only
git describe --tags --exact-match 2>/dev/null || true
Nie przełączaj brudnego katalogu Jeżeli git status --short pokazuje zmiany, najpierw je zachowaj na osobnym branchu albo wykonaj nowy clone. Nie używaj resetu do usuwania nieprzejrzanych zmian.

Profil workers jest bezpieczną pętlą dry-run Sam start Compose rejestruje role, odpytuje stan i zapisuje diagnostykę, ale nie wydaje polecenia Codex. Gdy Scheduler utworzy kwalifikujący się durable assignment, jawnie dopuść jeden host-side job dla właściwej roli.

agentic worker run-once \
  --role developer \
  --execute \
  --codex-execution-mode host_side

Zmień developer na rolę przypisaną przez Scheduler. Komenda nadal sprawdza status Jira, zależności, kontekst, workspace, locki i limity. Nie uruchamiaj jej dla historii spoza READY TO START.

7. Uruchom wykonanie Codex na hoście

Logowanie i limit

Host · subskrypcja ChatGPT
codex login
codex login status
agentic codex-limits refresh
agentic codex-limits latest --json

refresh uruchamia lub łączy się z codex app-server, wywołuje account/rateLimits/read i zapisuje decyzję w durable store. Kod wyjścia 0 zezwala na pracę, 2 oznacza blokadę limitu, a 1 błąd i stan UNKNOWN.

Supervisor

Ciągła pętla hostowa
source .venv/bin/activate
PYTHONPATH=src python scripts/runtime/run_host_codex_supervisor.py \
  run-loop --json

Supervisor pobiera durable joby utworzone przez workery, ponownie sprawdza limity i wykonuje je przez Codex CLI. Aby tylko sprawdzić stan:

Status bez pobierania pracy
PYTHONPATH=src python scripts/runtime/run_host_codex_supervisor.py \
  status --json
Nie zamykaj procesu hostowego podczas aktywnej pracy Zatrzymanie supervisora zatrzymuje wykonanie Codex. Stan zostaje zapisany, a po ponownym uruchomieniu normalne bramki resume muszą zostać sprawdzone ponownie.

8. Jak rozpoczyna się przetwarzanie

  1. Product Planning i Architecture przygotowują zakres oraz pytania w PO Inbox.
  2. PO odpowiada, akceptuje stories i przenosi je do READY TO START.
  3. Scheduler sprawdza sprint, role, zależności, design gate, bugi, limity i locki.
  4. Właściwy worker tworzy lub pobiera assignment oraz host-side Codex job.
  5. Supervisor wykonuje job w izolowanym workspace.
  6. Developer otwiera PR; Review czeka na CI i merge'uje poprawny PR.
  7. Tester testuje dopiero po merge do main.
  8. Release Manager uruchamia regresję, retro i closure.
  9. PO podejmuje decyzję na poziomie release, nie zatwierdza każdego technicznego test case.
FUNNEL→READY TO START→IN PROGRESS→DEV COMPLETED→IN TESTING→TEST COMPLETED→ACCEPTED/DONE

9. Jak rozpocząć pracę nad taskami z Jira

Jira nie uruchamia Codex samym statusem W Release 1.2 story w READY TO START staje się kandydatem, ale potrzebuje jeszcze kwalifikacji Scheduler/Orchestrator oraz trwałego assignmentu. Pełny automatyczny łańcuch wszystkich ról bez sesji operatorskiej nie jest udowodnioną funkcją 1.2.

A. Przygotuj story w Jira

  1. Dodaj story do aktywnego sprintu i właściwego projektu.
  2. Uzupełnij opis, acceptance criteria, context pack, rolę, repozytorium i poziom złożoności.
  3. Dodaj zależności kierunkowo: prerequisite blocks dependent story.
  4. Dla UI dołącz zaakceptowany Design Reference i blokującą design story.
  5. Sprawdź, że nie ma otwartego PO Inbox blocker ani powiązanego nierozwiązanego buga.
  6. Jako PO przenieś story z FUNNEL do READY TO START.

B. Uruchom Orchestrator dla sprintu

Najpewniejsza ścieżka 1.2 to sesja Codex uruchomiona z katalogu platformy lub projektu docelowego. Skopiuj starter z ai_agents/session_starters/README.md i podaj projekt oraz sprint. Minimalny komunikat:

Start sesji Orchestrator
Start as Orchestrator for Jira project <PROJECT_KEY> and active sprint <SPRINT>.
Read AGENTS.md and ai_agents/roles/orchestrator.md.
Find eligible READY TO START work, validate dependencies, PO blockers,
context pack, role routing, workspace, Git credentials and Codex quota.
Persist one project-scoped durable assignment for the selected role.
Do not start work that fails any gate.

C. Sprawdź assignment i limit

Kontrola przed wykonaniem
agentic worker status   --assignment-store-root data/agent-state   --json

agentic codex-limits refresh
agentic codex-limits latest --json

Jeżeli assignment jest zablokowany, sprawdź powód w UI lub JSON. Nie twórz ręcznie drugiego assignmentu dla tej samej story i roli.

D. Dopuść właściwą rolę do wykonania

Przykład dla story developerskiej
agentic worker run-once   --role developer   --worker-id developer-1   --execute   --codex-execution-mode host_side   --check-integrations

W osobnym terminalu musi działać host supervisor:

Konsument durable jobów
PYTHONPATH=src python scripts/runtime/run_host_codex_supervisor.py   run-loop --json

E. Kolejne role

Sygnał w Jira/GitHubNastępna rolaWarunek
READY TO STARTDeveloper / Frontend / inna implementacyjnaDependencies, context, design i quota gates są zielone.
DEV COMPLETED + otwarty PRReviewPR istnieje, branch nie ma konfliktu, CI może zostać uruchomione.
PR po review zmerge'owany do mainTesterTester potwierdza merge SHA i testuje acceptance criteria.
TEST COMPLETED dla całego sprintuRelease ManagerBrak blokujących bugów; można budować zakres regresji.
Regresja i retro zakończoneRelease Manager / POClosure evidence istnieje; PO wykonuje akceptację release.

F. Gdy story wraca

  • Review odrzucone: Developer poprawia ten sam branch i PR; Review nie naprawia konfliktów.
  • Test nieudany: Tester tworzy i linkuje bug, dołącza evidence i cofa story do DEV COMPLETED.
  • Pytanie biznesowe: agent zapisuje PO Inbox blocker i pauzuje assignment.
  • Brak limitu: job przechodzi do paused_limit; po świeżym odczycie użyj agentic worker resume-paused.
  • Przerwanie hosta: uruchom supervisor ponownie; przed resume ponownie przechodzą quota, Jira, dependency i lock gates.

10. Codzienna obsługa PO

Najważniejsze polecenia
agentic po-inbox list --status open
agentic worker status --assignment-store-root data/agent-state
agentic worker failed-requests --codex-jobs-root data/codex-jobs
agentic codex-limits latest --json
docker compose ps
docker compose logs --tail=100 api operator-ui worker-scheduler
  • Odpowiadaj na pytania i approvals w Operator UI.
  • Jira pozostaje źródłem statusu pracy i zależności.
  • GitHub PR pozostaje źródłem kodu, review i CI.
  • PO Inbox przechowuje blokujące decyzje i audit trail.
  • Gdy agent wygląda na zatrzymanego, sprawdź kolejno: PO Inbox, Jira dependencies, quota gate, assignment lock, failed requests i logi.

Zatrzymanie i wznowienie

Bez usuwania danych trwałych
docker compose down

# ponowne uruchomienie
docker compose --profile operator up -d
docker compose --profile workers up -d

# po świeżym odczycie limitu
agentic codex-limits refresh
agentic worker resume-paused

Nie używaj docker compose down -v, jeżeli chcesz zachować dane PostgreSQL i Redis.

Końcowy test gotowości

  • Operator UI otwiera PO Inbox bez błędu fetch.
  • API health zwraca status: ok.
  • Workery wszystkich wymaganych ról mają stan running.
  • Codex limit refresh zwraca dozwoloną, świeżą decyzję.
  • Host supervisor widzi te same durable roots co kontenery.
  • Testowa story w READY TO START jest widoczna dla właściwej roli.
  • Branch testowy nie jest main, a GitHub pozwala otworzyć PR.
  • Po restarcie kontenerów PO Inbox i assignment state nadal istnieją.
